# 第二轮渲染性能优化

日期：2026-10-26。继续优化[上一轮基线](render-optimization-results.md)，以同一批
生成文件、相同输出、相同资源预算比较。没有新增长期图片／页面位图缓存，没有更换
字体后端，也没有调整三方图像门槛。

## 正式结果

相对上一轮同一批 **20 个通过三方门禁的非空组合**，rzpdf 首次页面耗时的配对
几何均值降低约 **15%**，重绘降低约 **25%**。每组五次独立进程试验、两次预热、
十次重绘；正式计时没有启用资源诊断，没有其他构建或测试与之并行。

| 操作 | 上一轮 rzpdf／PDFium | 本轮 rzpdf／PDFium | 本轮 rzpdf／MuPDF |
|---|---:|---:|---:|
| 首次页面 | 4.12× | **3.62×** | 2.68× |
| 显式保留页面重绘 | 1.85× | **1.40×** | 2.25× |
| 连续翻页 | 2.07× | **1.84×** | 2.60× |

大于一表示 rzpdf 耗时更多。连续翻页只有两类文件、两个 DPI，共四个配对组合。
重绘已经接近目标量级；**首次页面仍有明显差距，不能称为整体追平 PDFium**。
绑定、渲染后端和缓存表示不同，结果仅代表这些合成输入的原生 owned RGBA 工作负载。

| 重绘场景，单位 ms | 上一轮 rzpdf | 本轮 rzpdf | 本轮 PDFium |
|---|---:|---:|---:|
| 小 JPEG，144 DPI | 91.76 | **49.28** | 38.46 |
| Flate 图片，72 DPI | 82.26 | **40.09** | 10.71 |
| 密集矩形，144 DPI | 53.03 | **38.37** | 14.62 |
| TrueType 文字，144 DPI | 6.86 | **5.00** | 3.75 |
| 空白页，144 DPI | 5.84 | **4.08** | 1.75 |
| 曲线，72 DPI | 58.20 | 57.26 | 7.59 |

曲线没有明显改善，仍需进一步处理；不能以总体均值代替这一差距。正式结果未发现
旧有 28 个组合中首次或重绘中位数超过 10% 的退化。早期试验中出现的密集中文／
透明页面退化经过通路选择与保留起始清空处理，最后复测不再超过此门槛。

正式 **420 次计时全部成功**，无超时或 trap；三方门禁仍为 **22/28**，两组空白
不进入比例统计。全部 **28 个组合的选中页面尺寸与 RGBA 均和上一轮逐字节一致**。
既有六组图像差异仍排除，没有通过放宽门槛换取速度排名。

## CPU 与内存

在相同最终二进制上另外运行四类输入（144 DPI，三次试验）的 **36 次资源诊断**，
不将诊断计时混入上面的正式排名。三套进程的重绘 CPU／墙钟比中位数均约 **0.999**，
没有观察到持续多核执行优势；这不证明内部从未启动其他线程。

小 JPEG 144 DPI 的阶段 RSS 如下，单位 MiB；阶段值取三次中位数，峰值取最大值。

| 引擎／适配器 | 初始化后 RSS | 首次输出后 RSS | 重绘后 RSS | 整个 worker 峰值 |
|---|---:|---:|---:|---:|
| rzpdf | 2.26 | 34.62 | 34.70 | 34.77 |
| MuPDF／Python | 38.75 | 62.79 | 62.88 | 63.02 |
| PDFium／Python | 15.65 | 40.88 | 40.94 | 41.09 |

Python 运行时影响基线；惰性代码页、allocator 保留页和中间对象生命周期也不同。
**不能据此断言 rzpdf 的纯引擎分配更少，也不能把阶段差值当作精确分配量。**
相同不采样设置下，小 JPEG 的 rzpdf worker 峰值为上一轮 34.82→本轮 34.75 MiB，
大扫描图为 118.24→118.08 MiB；没有观察到显著 RSS 增长。这不是浏览器线性内存测量。

## 实现

- **图片 Decode／Range 查表**：8 位 ICC 图片的解码值只依赖分量和输入字节。
  用固定 4×256 项 f32 表保存原 f64→f32 的结果，批次中按分量取值，减少逐像素
  浮点计算和取模。ICC 变换、意图、Range 及精度要求不变；蒙版／Matte 路径保持原样。
- **合并覆盖区间**：将相邻行中横向范围和 A8 覆盖值完全相同的 run 合并成矩形，
  继续交给 Skia 整数 blitter。矩形互不重叠，每个采样恰好提交一次。固定数组限制
  暂存大小；不改变 canonical cell、曲线细分或分块坐标。
- **选择白底合成通路**：全幅整数裁剪的 premultiplied RGBA／BGRA 白底满足
  `c += 255-a`。稀疏页和不透明图片利用透明零块／不透明像素快捷处理；混合 alpha
  密集的页继续使用 Skia SIMD 通路。其他底色、部分裁剪等保留通用合成。
  写入前通知 Skia 保留快照的 copy-on-write。
- **保留页面起始清空**：曾尝试依赖 allocator 的零初始化。定向对比表明，本机
  密集绘制保留起始透明清空更快，最终恢复原调用。语义上的重复写入不代表没有性能价值。
- **资源诊断**：可选 `--diagnostics` 记录初始化后、首次输出后和重绘循环后的 RSS，
  以及首次／重绘阶段的进程 CPU 时间。RSS 查询位于操作计时之外；正式速度排名与
  资源诊断分开运行，减少进程查询对缓存、调度和频率的干扰。

这轮暂存表及覆盖区间数组均为固定大小。没有通过扩大缓存或提高原有资源上限获得收益。

## 验证方法

- 渲染库 **96 项**测试通过：包含全部 alpha 的白底合成对照、快照保留、裁剪回退、
  密集 alpha 通路选择、区间无重叠重建、既有透明／分块／字体／图像测试。
- 图片 **26 项**定向测试通过；既有依赖私有 Financial 文件的 1 项 ignored 不计为通过。
- 基准工具 **6 项**测试通过，新增阶段 RSS 与峰值分离、CPU／墙钟比汇总验证。
- 严格工作区全目标 Clippy、格式和 diff 检查通过；未重跑全量工作区集成测试。
- 固定工具链优化 WASM 构建通过；直接调用／真实 Worker **56 项**组合检查通过。
  另有既有 ICC、错误恢复、稀疏 CID、循环颜色与 Type3 专项的两条浏览器通路通过。

浏览器检查属于正确性验证，不是 WASM 与 PDFium 的速度排名。文字的 CoreText／
FreeType 差异、大 JPEG 的浏览器降采样政策继续按上一轮边界单独处理。

## 复现与产物

安装和构建见[基准指南](benchmarking.md)。正式计时使用与旧基线相同的不采样设置：

```sh
cargo build --release --locked -p render --example benchmark_render
python3 scripts/benchmark_pdf.py \
  --manifest output/benchmark-corpus-v2/manifest.json \
  --output output/benchmark-round2-release-20261026 \
  --trials 5 --warmup 2 --repeats 10
```

输出目录必须为新目录。资源诊断另行使用 `--diagnostics`，可配合
`--case jpeg-small ttf-text rectangles curves` 缩小范围。
其 RSS 包含运行时、惰性代码页及 allocator 保留页；阶段增加量不是纯引擎分配量。
CPU 时间汇总进程内线程，CPU／墙钟接近一只能说明没有看到持续多核优势。
本轮没有强制 CPU 亲和性或线程数，也没有进行逐时活跃线程跟踪。

最终产物：

- `output/benchmark-round2-release-20261026/`：正式 `report.md`、`summary.json`、
  `raw.jsonl`、`quality.json`、源码／二进制指纹、PNG／RGBA 和 `before-after-check.json`。
- `output/benchmark-round2-resources-20261026/`：独立资源诊断，新增 RSS／CPU 字段位于
  `summary.json` 和每次试验的 `raw.jsonl`。
- `output/render-profiles-round2/`：本轮初始 CPU 采样。
- `output/webassembly/render-round2-final-build.json`：最终优化 WASM 构建；
  `render-benchmark-regression/report.json` 与 `icc-browser/report.json`：浏览器验证。
