# v0.14 预算与规模基线

`v014_benchmark` 在 debug profile 测量关联条目 1／100／1000、单文件 0 B／1 KiB／1 MiB、页面 owner 1／10／100，以及八文件各 64 KiB 累计载荷。每种输入保存三种布局，共 30 行 JSON。构建、读取提取和保存耗时分列；Strict 重开后检查列表大小，编辑／读取 pool 返回零。

进程 RSS 和 wall／user／sys 由 `/usr/bin/time -l` 单独记录，writer 使用自己的预算，不包含在编辑池峰值内。测量与其他最终门禁并发，本机 debug 数据不构成生产延迟、线性复杂度或压缩比保证。最终冻结源码的 benchmark 已退出 0，证据为 `tmp/pdfs/v014-final1/benchmark.log`、`benchmark-stderr.log` 和对应 receipt。

30 条均断言 retained=0。整进程 80.57 秒 wall、62.78 秒 user、1.63 秒 sys，maximum RSS 为 23232512 bytes。wall 与单段计时之差包含启动、调度及保存／重开，不归因于一个编辑算法。1000 条逐项创建绑定实测约 64.85 秒，重复读取和快照成本明显，不作交互式响应保证；后续可另立批量 API／计划复用优化，不能为提速删掉身份或预算校验。

新逻辑显式跟踪返回列表、字符串、对象副本、解码载荷和事务快照；创建／补丁还有保守 scratch。原始 caller 输入、持久 store 增长、旧 API／缓存与原生分配不由一个编辑池完整覆盖，不把 tracked peak 当作全进程 RSS。逐个绑定时会重新读取当前 owner 和已有关联，批量创建仍可能产生非线性成本；当前无批量事务接口或吞吐 SLA。
