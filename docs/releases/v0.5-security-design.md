# V05-B / C: security implementation decisions

Status: implementation contract, not an acceptance claim. 2026-10-14.

## Password protection

- Standard handler only: V=5, R=6, AESV3 (256-bit). Other handlers and revisions
  return an explicit unsupported-security error, not an invalid-password error.
- Parse the unencrypted Encrypt dictionary and authenticate before opening the
  Catalog or publishing decrypted objects. No authentication bypass via a
  tolerant parser mode or direct mutation of trailer Encrypt.
- Password input is UTF-8 with RFC 4013 SASLprep, at most 1024 input bytes and
  127 normalized bytes (longer input is rejected, never truncated). Non-ASCII,
  empty user passwords and prohibited characters have independent fixtures. Errors and
  Debug output never include passwords, file keys, or plaintext fragments.
- Keep authentication role and permission reporting separate. Owner access can
  manage protection; user access must pass an explicit editing policy. Permission
  flags are not DRM. Expose conservative low-level/high-level enforcement limits.
- Decrypt ordinary indirect objects once before source caching. Objects inside
  an object stream inherit its outer decryption and must not be decrypted again.
  Xref streams, Encrypt, explicit Crypt/Identity and clear metadata are special
  cases with dedicated tests, not exceptions inferred from successful rendering.
- Default full save preserves protection independently of mutable trailer
  contents. Remove and Set require explicit policy; replacement protection and
  removal require owner authorization for an already protected document.
- New salts, keys and IVs use the operating-system random source. Ciphertext
  lengths and temporary allocations share existing operation-budget accounting.
  Controlled secret buffers are zeroized; no promise covers caller-owned
  passwords, all compiler temporaries, OS swap, or persistent plaintext caches.
- AES/SHA implementations come from RustCrypto dependencies, not local cipher
  implementations. Existing ZeroPadding helpers are not the PDF AESV3 encoder.
- New AES-256 output declares PDF 2.0. Authenticated PDF 1.7 with Adobe extension
  level 8 can be preserved; arbitrary PDF 1.7 AES-256 input is rejected.

## External signing

- Preparation owns immutable final bytes, ByteRange, Contents reservation,
  digest and a document identity/revision stamp. No source in-place update.
- The signer receives the actual detached content or a clearly identified
  digest contract; a raw RSA result is not a CMS container.
- CMS completion checks structure, SHA-256 messageDigest, signer binding and
  cryptographic integrity using maintained implementations. This is not a
  certificate-trust verdict. Freeze a bounded key/signature algorithm matrix;
  reject everything outside it rather than treating it as verified.
- Do not consume a preparation token on a recoverable failure. On success,
  prevent reuse. Recheck the document stamp at completion.
- Existing signed inputs are protected at mutation and save boundaries, not
  only at a convenience API. Do not claim DocMDP or FieldMDP authorization.
- Synthetic test certificates only; independent pyHanko validation is mandatory.

Frozen completion matrix: detached DER CMS SignedData, exactly one signer,
SHA-256, required contentType/messageDigest signed attributes, embedded signer
certificate selected by issuer and serial, RSA PKCS#1 v1.5 with 2048..8192-bit
keys. CMS is capped at 64 KiB, certificates at 16 and attributes at 32. RSA-PSS,
ECDSA and subject-key-identifier selection are explicitly unsupported in v0.5.
DER/CMS parsing uses RustCrypto cms/der/x509-cert; RSA public verification uses
ring. There is no private-key operation or OpenSSL runtime dependency in core.

Preparation uses an isolated unsigned snapshot and a private incremental writer
capability; public incremental save never permits signature overlays. Contents
and ByteRange are located by parsing the actual xref-addressed signature object,
not a whole-file marker search. Fixed-width replacement changes no offsets.
Reports bind the excluded span to that exact Contents lexical value and check
the covered revision's xref/EOF; they still say NotPerformed, never trusted.

Signing rejects hybrid-reference input/history, while A continues to support
hybrid incremental saves. An immutable CrossRefTable provenance flag is ORed
across merged Prev revisions and survives trailer transfer. Mutable XRefStm
removal cannot bypass this restriction. Explicit full rewrite and reopen is the
normalization workflow; no hidden rewrite during preparation. pyHanko's strict
validation deliberately rejects hybrid signatures because different readers may
interpret them differently; see its
[changelog](https://github.com/MatthiasValvekens/pyHanko/blob/master/docs/changelog.rst).

High-level annotation and assembly operations additionally check their own
permissions. Ordinary edits conservatively also require modify; form filling is
a scoped private exception requiring fill_forms. Low-level object mutations
enforce modify but cannot reliably infer annotation/assembly semantics. Printing,
copying and accessibility permissions are reported for the host application,
not enforced as access control over plaintext already given to it. Owner access
bypasses these advisory editing flags. No DRM guarantee is made.
