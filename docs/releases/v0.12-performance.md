# v0.12 structure budget and performance baseline

The benchmark is a fixed synthetic workload, not a speed or compression target. `pdf/examples/v012_benchmark.rs` generates 99, 100, 101, 1,000 and 10,000 small string objects with 1,024 free-number holes and one high live object. Each scale measures Classic, independent XrefStream and packed ObjStm using Preserve and FlateUnencoded, explicit read-only recovery, and three xref-stream incremental revisions.

```sh
cargo build --locked -p pdf --example v012_benchmark
/usr/bin/time -l target/debug/examples/v012_benchmark > benchmark.jsonl 2> benchmark-rss.log
```

Each of the 50 JSON records reports profile, scale, elapsed microseconds and tracked peak bytes. Save rows include output length; recovery rows include input length and scan steps; append rows include round and complete output length. Saved output is Strict-reopened and page-count checked; each budget returns to zero after its owner is dropped. Input construction, reopening, untracked legacy/native allocations and benchmark print overhead are not part of a save timing. These are debug-profile local numbers, not statistically controlled throughput results.

The 99/100/101 scales exercise counts around the 100-member grouping policy together with ordinary page objects. Exact member/header byte and 1 MiB grouping boundaries remain tested in the object-stream unit/integration tests; the benchmark itself does not assert that a selected scale maps to exactly one container. Sparse numbering includes free-chain/index cost rather than counting only live objects. Preserve versus Flate records encoding tradeoffs without a fixed compression-ratio promise.

## Enforced limits and negative evidence

| Component | Bounds and assertions |
|---|---|
| Full xref stream | Size/object count, 13-byte records, raw/decoded bytes, output size and shared tracked operation allocations; exact/low-one, temporary ID and retry cases in `v012_xref_output` |
| ObjStm | At most 100 members / 1 MiB raw group including index/header/body; independent fallback for ineligible/oversized members; compression and temporary overlap accounted in writer tests and `v012_object_streams` |
| R6 layout | Single container encryption, AES IV/padding reservation, crypt-filter exceptions, RNG failures and retries; `v012_layout_security` plus security/writer units |
| Incremental | Sparse changed/free/self records; source prefix and output ceiling, shared budget release and three rounds; `v012_incremental_stream` and `v011_encrypted_incremental` |
| Recovery | 64 MiB / 100,000 candidate ceilings intersect parser limits; `16*n+1024` byte/probe work and direct stream Length; exact scan/candidate/input limits, low-one and failed same-pool retry in `v012_recovery` |
| Diagnostics | 1,024 distinct events / 1 MiB tracked pool intersect max_operation_bytes; fixed reason records, dedup, exact first allocation and growth overlap refusal; parser diagnostic unit tests |

The recovery source Vec retains its capacity reservation; conservative index growth and per-object budget-aware parsing share the supplied pool. Some existing parser/context/cache allocations remain outside it. Layout and recovery measurements must not be advertised as an end-to-end allocator or RSS limit. Recovery byte-work accounting covers lexical reads/lookahead and payload blocks, not every CPU instruction or downstream rasterization.

Actual final-run records and RSS log paths are entered in [acceptance](v0.12-acceptance.md). macOS RSS is a process-wide high-water mark including runtime and all scales, not a per-operation sum. No Linux/Windows RSS values, release-build comparisons, hardware-neutral performance, linear scaling or general rendering speed claims are inferred.

## Local measured baseline

`tmp/pdfs/v012-final2-benchmark.jsonl` contains all 50 records, process exit 0; `v012-final2-benchmark-rss.log` records 43.02 seconds wall time and 18,292,736 bytes maximum resident set size for the entire process. The run shared the host with compilation/independent gates, so timing differences must not be interpreted as comparative speedups. Earlier `v012-final-benchmark` records are candidate history, not the final baseline.

The 10,000-small-object rows are:

| Operation | Bytes | Microseconds | Tracked peak bytes |
|---|---:|---:|---:|
| Classic / Preserve | 639,892 output | 78,182 | 2,034,184 |
| XrefStream / Preserve | 562,766 output | 64,000 | 1,149,485 |
| ObjStm / Preserve | 488,138 output | 111,480 | 1,600,314 |
| ObjStm / Flate | 221,418 output | 186,469 | 662,202 |
| Recovery | 639,892 input | 319,514 | 3,392,436 |
| Incremental round 3 | 680,668 complete output | 344,170 | 2,348,493 |

Recovery used 895,537 charged steps at this scale. These numbers describe this exact original synthetic recipe and debug binary; use the JSON for every scale/encoding/round. All output readback and post-drop zero-live-budget assertions passed.
