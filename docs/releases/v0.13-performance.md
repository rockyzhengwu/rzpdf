# v0.13 Budget and performance baseline

This is one debug-profile observation on macOS 13.7.8 x86_64, with other build
and verification work running on the same host. It is not a production latency,
scaling, compression-ratio or whole-process memory guarantee.

## Method

`v013_benchmark` creates 1, 100 and 1000 registered OCGs, writes a default ON
configuration with all but the first group in OFF, appends one selected path,
and saves Classic, XrefStream and ObjStm output. Every output is reopened in
Strict mode and its group count is asserted. The edit pool has 128 MiB capacity;
all nine observations assert zero retained edit reservations after each call.
Save uses the existing writer's own budget, not the edit peak column.

Final source list: 645 inputs, `v013-final3-source-manifest.sha256`, SHA-256
`eddad4a8f18ce46caa6d985cd7212f4197479f817e4c254737b4a4e0bd24891d`.
The completed command exited 0:

```sh
/usr/bin/time -l target/debug/examples/v013_benchmark \
  > tmp/pdfs/v013-final3-benchmark.jsonl \
  2> tmp/pdfs/v013-final3-benchmark-rss.log
```

## Observations

Creation and editing times are shared by the three layouts in each group-size
row, not repeated work to add together. Times below are microseconds; sizes and
reservations are bytes.

| Groups | Create | Configure and append | Edit tracked peak | Classic / xref / ObjStm bytes |
|---|---|---|---|---|
| 1 | 249 | 1328 | 2106649 | 790 / 818 / 881 |
| 100 | 105813 | 92643 | 2200007 | 11475 / 10813 / 10166 |
| 1000 | 10440212 | 10794087 | 3188389 | 113195 / 106235 / 99110 |

Save times for Classic / xref / ObjStm respectively were 768 / 431 / 575 at one
group, 5711 / 5918 / 6920 at 100, and 47754 / 78882 / 70339 at 1000. Output is
Preserve-encoded for this baseline; the independent gate separately exercises
Flate and R6.

The entire process took 74.09 seconds wall time, 19.12 user and 0.74 system;
maximum resident set size was 14376960 bytes. Wall time includes process launch
and scheduling outside the timed operations. Do not attribute the difference
to the editing algorithms or compare it directly with another host's timings.

## Accounting and known cost

The edit tracked peak includes a conservative 2 MiB scratch reservation, not
2 MiB of measured allocations. New owned dictionaries, parsed content and
transaction snapshots have additional reservations. Caller input, persistent
store growth, existing read-model/evaluator allocations, source caches and
native resources are not all tracked. RSS and tracked peak measure different
things and must not be substituted for one another.

Registration is re-read while creating groups, and configuration validation
re-reads it for individual members. The current bounded implementation therefore
has substantial repeated work near the 1024-group ceiling; this baseline does
not promise linear scaling or interactive latency for large batches. A future
optimization can validate one immutable registry snapshot per operation without
weakening membership/stamp checks. No numerical speed target was an acceptance
requirement for this release.

The integration tests additionally check the exact 1024-group / 256-alternative /
4096-node boundaries, one-less-than-required versus exact operation budget,
rollback, release and retry. See the [boundary](v0.13-boundaries.md) and
[acceptance record](v0.13-acceptance.md) for final gate results.
